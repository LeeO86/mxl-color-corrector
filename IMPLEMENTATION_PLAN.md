# Implementation notes

Pinned MXL: `dmf-mxl/mxl` `release/v1.1` at `218ddaa0a08c12ffe75fc475ae65aa3d9eef16d7`, Fabrics off. The library is built from that git tag inside CMake (same sources the platform pin builds).

## Behaviour choices

* **Slice commits.** On this revision `mxlFlowWriterOpenGrain` clears `validSlices` only when the index is not already the open grain, and `mxlFlowWriterCommitGrain` leaves the grain open while `validSlices < totalSlices`. The worker opens a grain once, writes the newly committed input lines, and commits with an updated `validSlices`. The struct returned by `OpenGrain` is kept so `version`, `size`, `grainSize` and `totalSlices` are not zeroed. Input grain flags, including `MXL_GRAIN_FLAG_INVALID`, are copied onto the output. An invalid grain is copied through, not replaced with black. Flow directories are `<id>.mxl-flow/`, which is the layout this MXL revision writes.

* **Interlaced grain rate.** MXL rejects an interlaced `grain_rate` other than 25/1 or 30000/1001. The corrector reports whole-grain fallback for any non-progressive `interlace_mode` once the flow can be opened.

* **Co-siting.** v210 chroma belongs to the even luma sample. Odd luma uses that same pair. Output chroma is the even sample's result. A neutral matrix with legal samples is a byte copy, including line padding.

* **Matrix.** The RGB affine correction and the saturation scale are folded with the BT.709 matrices into one 3×4 fixed-point matrix (1/65536). Neutral controls force an exact identity. RGB gamut clip is a separate per-pixel step and does not round-trip samples that are already inside 0…1. Its conversions multiply by reciprocals (no divisions); the SIMD paths first test a register of pixels in 32-bit fixed point and skips the exact double-precision test when all are clearly inside the cube (1.0.4, docs/performance.md). `clip=off` still limits codes to the 10-bit container, 0–1023. Extended clip is 4–1019.

* **Read offset.** Slice mode follows the writer's head (offset 0). Whole-grain mode reads `CC_READ_OFFSET_GRAINS` behind the head, default 1, so the grain is complete. Fallback reasons are `interlaced`, `no_slice_commits` (four grains seen only as complete) and `slice_layout` (slice size is not an integer number of v210 lines that divide the frame). The change is logged once.

* **Added latency.** The histogram is the time from the slice becoming visible (`mxlFlowReaderGetGrainSlice` has returned) until `mxlFlowWriterCommitGrain` returns for the lines just written. A later slice does not reprocess lines already committed. The wait for the source to publish the next slice is not included.

* **NMOS.** The node is an in-process IS-04 v1.3 and IS-05 v1.1 implementation with BCP-007-03 `video/v210` and `urn:x-nmos:transport:mxl`, deterministic UUIDv5 ids, and static registry registration. `NMOS_DNS_SD=true` is accepted and logged; this build does not advertise over DNS-SD. Receivers activate even when the domain or flow is missing (`waiting`, backoff to 2 s) and the IS-04 `subscription` follows the activation. A new input geometry mints a new output flow id.

* **Colour wheels and RGB pots (1.1.0).** `+x` is red (Cr), `+y` is blue (Cb). The R, G, B trims are the only parameters; the wheel is a view of their chroma part. `trimLuma` (`Kr·r + Kg·g + Kb·b`) splits the trims into a luma part and a tint; `trimsToWheel` maps the tint back with the scale of `wheelToTrims` (rim = 20 % white, 5 % black towards blue, unchanged so 1.0 clients get the same tint for the same `x, y`) and pins a larger tint to the rim in its direction. A wheel patch keeps the luma part and is clamped to ±100 %; numeric trims in the same patch win; the wheel position is recomputed after every patch (`src/store.cpp`). 1.0 dropped the luma part on every wheel move and on every restart (the stored wheel position won over the stored trims), and read the wheel from `r` and `b` without removing the luma, so R = G = B moved the dot. Decision: the wheel keeps its 1.0 span rather than covering ±100 %, for fine balance and an unchanged meaning of `x, y`; the pots cover the full range with 0.1 % steps. The UI shows the trims as pots or as the wheel per section (localStorage `mxl-color-corrector.view.white|black`) and renders only server state, except while a fader or the wheel is dragged.

* **Ranges (1.1.0).** The operators asked for pedestal and one more control at ±100 %. Every control that is a percentage of the signal level is now ±100 %: white trims (were ±20), black trims (±5), pedestal (±10), brightness (±20). Gain and saturation are ratios and keep 0–200 %. The extreme corner of the matrix (gain 200, saturation 200, pedestal and brightness −100, mixed trims) has a lane sum of 1.64·10⁹ < 2³¹, so `fits32` keeps the AVX2 block path and `buildMatrix` never clamps a coefficient; the scalar path is 64-bit. `clip` still bounds the output. The unit tests walk all 1024 corners (AVX2 = scalar, legal output, 1 LSB of the reference).

* **Web UI and widgets (1.1.0).** `web/src` follows mxl-webrtc-monitor 1.3.0 and mxl-replay 1.4.0 (same `style.css` base, `Pill`, `Segmented`, `IdCode`, the store with WebSocket and polling fallback, `#hash` tabs). Control changes go over the WebSocket, at most 30 per second, merged per channel (a trim object carries only the changed channel, so two pots moved quickly do not undo each other); REST while the socket is down. `/widget/<id>` serves the same single-file page; `main.js` mounts `WidgetPage` for those paths. `HttpResponse::cors` lets the widget routes leave out the API's `Access-Control-Allow-Origin: *`. There is no video preview (JPEG thumbnails only), so the preview contract (`PREVIEW_*`, a MediaMTX child, the transform crop) is not applicable.

* **WebSocket clients (1.1.0).** Only a client's own thread closes its socket; `broadcast` shuts a failing one down (send timeout 1 s) and removes it. Before, `broadcast` closed the descriptor while the thread still polled it, so the number could be reused by a new HTTP connection whose request the old thread then read (empty answers), and a client gone without a close frame made its thread spin.

* **SIMD levels (`CC_SIMD`, unreleased; platform plan G).** One block kernel, `src/color/process_kernel.inl`, written over a traits type and compiled three times: AVX2 (`process_avx2.cpp`, 8 groups per step), AVX-512VL on ymm and AVX-512 on zmm (`process_avx512.cpp`, 8 and 16 groups; a zmm line ends with one ymm block when 8–15 whole groups are left). Decisions:
  - *Function attributes, not file flags or a library.* Each kernel function carries `__attribute__((target(...)))`; the build stays plain x86-64 (no `-march`). With a `-mavx2`/`-mavx512f` file flag (1.0.1–1.1.1 used `-mavx2`), the inline functions from headers that such a file instantiates (`std::min`, the v210 helpers) can be emitted with those instructions and picked by the linker for the scalar code; with attributes they stay baseline code. The CI runs the unit tests under Intel SDE as Haswell, which stops on any AVX-512 instruction outside the AVX-512 code. Google Highway would do the same with a dependency for one kernel of about 40 operations; GCC `target_clones` cannot express the mask types that differ per level. GCC does not give a lambda the target of its enclosing function, so the kernel has none (`dot8`'s helper became `mulAdd`).
  - *Code shape.* Named struct members instead of arrays of vectors (GCC 13 keeps such arrays on the stack); `always_inline` on the per-block steps (GCC left the pair functions out of line: AVX-512VL 2.13 → 1.68 ms per frame); no gathers (Downfall microcode). `-ffp-contract=off` on both kernel files, so the gamut clip's double arithmetic never becomes FMA.
  - *Bit-exact.* The rows are the same 32-bit sums in another order (the chroma pair's part m1·Cb + m2·Cr + m3 + 32768 once, then m0·Y per sample); the clip limits lie in 0–1023, so one clamp does both of the scalar code's clamps and "clipped" is "the clamp changed the lane"; the gamut clip repeats the scalar double operations; the inside test's 16-bit multiplies are exact for every lane it can keep (codes within the legal ranges, coefficients below 2¹⁵). Unit tests compare every level with the scalar path on 21 widths, edge codes, set padding bits, padded strides and slices, with and without statistics.
  - *Clip statistics.* The engine always asks for them (`clipped_ratio`). In 1.1.1 they recomputed the odd samples' chroma rows in full and counted with movemask and popcount per register: 2.50 instead of 1.60 ms per 1080p frame (AVX2, lab). Now the odd chroma is one multiply per row on top of the shared part, AVX2 counts unchanged lanes in a vector per line and AVX-512 popcounts masks. The scalar path added to `stats` per pixel through a pointer the compiler must assume aliases `dst`; it counts per line now.
  - *Detection and setting.* cpuid (AVX2; AVX-512 F, VL, BW, DQ) and XGETBV (XCR0 bits 1, 2 and 5–7: SSE, AVX, opmask and zmm state). The family for `auto`: Intel without VBMI2 = `skylake-sp` (Skylake-SP, Cascade Lake, Cooper Lake), Intel with VBMI2 = `icelake+`, AMD family 19h = `zen4`, 1Ah and later = `zen5`. `CC_SIMD` is a setting like the others (invalid → 78); a level the CPU lacks falls back to the best one below it with a warning. `processV210` reads the level from an atomic (1.1.1 ran cpuid on every call). Start log line, `simd` in the status, `mxl_color_corrector_simd_level{level}`.
  - *auto per family (decision rule of plan G: ≥ 15 % less CPU for the process and < 3 % loss for a workload on the same core).* Skylake-SP class: `avx2`. On the lab Gold 6136 `avx512` saves 19 % (clip off) and 40 % (RGB gamut clip on) but runs in frequency licence 2 (2.7 GHz), and the core's other hyperthread loses 3.4–4 % against `avx2`; `avx512vl` keeps licence 1 and costs the neighbour nothing but saves 7 % (off; 20 % with RGB gamut clip on bars, about 8 % on camera pictures). Judgement: one `auto` per family for the default load (clip off); a per-path `auto` (`avx512vl` when RGB gamut clip is on) would follow the rule on bars but not on camera pictures. Ice Lake and later, Zen 4 and Zen 5: `avx512`, from published behaviour (no frequency licence to speak of, Zen 4 double-pumps 512-bit work at full clock) and the CI's runners (kernels 1.5–1.85× faster than AVX2 on Emerald Rapids, 1.9–2.2× on Zen 5); the co-located cost is not measured there, and Zen 4 not at all (the runners' VM hides AVX-512). Numbers in `docs/performance.md`.

* **Re-created source flows (1.2.1).** 1.2.0 closed its reader only on a failed read, but it read a grain only once the head had reached it (`head < index` → sleep 1 ms). The head of a deleted or re-created flow stands, so it never read past it, never saw `MXL_ERR_FLOW_INVALID`, and the channel and its output stood until an IS-05 disable and enable (seen on small, 2026-10-15: the multiviewer showed `no_signal` and the replay camera fed from the corrector stopped). Now `src/mxl_source.cpp` (`SourceReader`) checks a standing head (MXL's own check through a non-blocking read one past the head; the data file's inode before the first grain) and `src/engine.cpp` re-opens on the schedule of mxl-decklink 1.0.4 (0, 100, 200, 500 ms, then 1 s), with a 20 ms look for the flow's file in between so a returning flow is read within one check. Decisions: one MXL instance per channel and source domain rather than per output (mxl-decklink 1.0.4 bound one instance per output channel, so a channel with video and audio in different domains could not open its readers); a corrector channel has one source, and the instance follows the route. The held grain is read back once from the channel's own output flow when the source is lost (no copy per grain in normal running). The held output stops at the new flow's first head; the next output index is the later of the new head and the last held grain + 1 (within 8 grains), so the output never goes back. A read that is too early while the head is already past the index (checked with a second, non-blocking read, since the writer may have just finished the grain) skips that grain: whole-grain mode re-synced to `head - 1`, which a re-created flow never wrote, and waited until the late check fired at half a ring. A killed writer leaves a valid flow that is no longer written. The first version did not hold it, and the lab showed a 1.9 s output gap until the restarted player replaced the flow. The brief says the output never stops, so the channel now also holds after four grain periods (at least 100 ms) without a write. It checks `lastWriteTime`, which every slice commit sets, not the head, which stands while a slow writer fills a grain. When the flow is written again it re-syncs. While holding it does not read, so no output grain is written twice. Holding has no time limit: a source gone for good shows as a frozen picture downstream, with state `holding` here.

* **State.** `/config/state.json` (or `CC_STATE_DIR`) stores both A/B slots and presets. If the directory cannot be created the process keeps running and logs a warning.

* **History.** Output domains are created with a 200 ms grain history so a 1080p50 flow stays near 60 MB.

Performance figures are in [docs/performance.md](docs/performance.md). They were measured on the build machine, not on a Dell Precision 3930. A lab run on a Xeon Gold 6136 (2026-10-03, `docs/performance.md`) reached only about 37 grains/s per 1080p50 channel at one core.
